# Review — `Scope_SharePoint_Flow_Truth_Persistence`

**Subject** `Scope_SharePoint_Flow_Truth_Persistence_CONNECTOR_FIXED_PASTE_READY_PRETTY.json`
— a Power Automate designer clipboard package, 25 actions, 13 of them SharePoint connector calls.

**Stated purpose** to generate a complete, accurate and reliable database of the platform's
endpoints and flows.

**Verdict** the package cannot be saved by the designer, and if the conditions that stop it saving
were removed it would not do what it says. Run through this repository's own gate,
`scripts/verify-designer-paste.mjs --strict`, it produces **52 failures**; all thirty-four
packages already committed produce none. Nineteen further defects are behavioural and no
existing gate looks for them. Two of the findings are security findings: the record it writes to
SharePoint carries the flow's own trigger URL and signature token, in a record that asserts it
carries no credentials.

The rebuilt package is `docs/deployment/governance/flows/DGO_FLOW_TRUTH_PERSISTENCE.designer-paste.json`,
generated by `scripts/build-flow-truth-persistence.mjs` and held to these findings by
`tests/flow-truth-persistence.test.mjs` (73 assertions, `npm run test:flowtruth`).

## 2. Blocking defects — the flow will not save

### B1 · The three target lists exist nowhere in the estate

`NITDA Flow Truth Registry`, `NITDA Flow Truth History` and `NITDA Flow Truth Artefacts` appear in
none of: the 326-list tenant capture, the twelve provisioned portal lists in
`portal-field-spec.json`, the ten governance lists in `sharepoint-provisioning-spec.json`, or the
twelve adopted lists in `internal-field-evidence.json`.

That is not a deployment detail to be sorted out later. The package writes **28 `item/<Column>`
parameters** to the history list and **28** to the registry list. The designer validates every
one of them against the connector's operation definition for that list **at save time** and
refuses the whole flow:

> Flow save failed with code `WorkflowOperationParametersExtraParameter` and message
> 'The API operation does not contain a definition for parameter `item/RunRecordJson`.'

Because it fails at save, no run-time fallback can catch it — the flow never runs. This is the
same failure `scripts/lib/designer-paste-builder.mjs` documents at length after all fourteen of
this repository's packages once hit it.

**Severity** Blocking. **Fix** provision the lists before the package can exist — and see §5,
because they are the wrong lists.

#### Addendum, 2026-09-10 — the finding above is measured against the capture, not against today

Two browser scripts that create exactly these three resources were reported executed against the
tenant on 2026-09-10. They are held verbatim at `docs/reference/out-of-band/` and recorded as
**GOV-11** in `docs/reference/governance-estate-position.json`.

What that does and does not change:

- **It does not make B1 wrong.** Every negative above is measured against the 2026-08-18 capture
  and the four specifications, and all five still contain nothing by these names. B1 is an
  accurate statement about the estate's own record.
- **It does mean B1 is no longer a statement about the live tenant.** The record is now three
  weeks and one out-of-band execution behind, and this addendum is the only thing connecting the
  two.
- **It does not resolve B1's blocking status.** The designer refuses the package because the
  connector has no operation definition for those columns. Provisioning three lists on an
  unrecorded site with `createfieldasxml Options: 0` — no `AddFieldInternalNameHint` — does not
  reliably produce the internal names the package addresses. It may have produced
  `Registry_x0020_Key` where the package writes `item/RegistryKey`, which fails in the same place
  for the same reason.
- **It does not resolve §5.** These are still the wrong lists. The estate specifies seven for this
  capability, in `http-flow-registry-spec.json`, and provisioning three more beside them is the
  GOV-02 condition one level up: two implementations of one database, each invisible to the other.

**Do not treat this addendum as evidence that the lists exist.** Execution was reported, not
observed, and neither script recorded which site it wrote to. Run
`scripts/verify-flow-truth-provisioning.browser.js` — read-only, asks both candidate sites — and
record what it prints under GOV-11 before anyone acts on B1 either way.

### B2 · Lists are targeted by display title, not by GUID

```json
"table": "NITDA Flow Truth History"
```

Across the deployed definitions there are **273 SharePoint list actions and not one** targets a
list by title; all 273 carry a GUID. The estate's gate checks exactly this, and the reason is
in the tenant: three lists are called `DGO_UserDirectory`, three `DGO_EndpointRegistry`, two
`DGO_UserRoleHistory`, and in each case only one is `adopted`. A title is ambiguous, is not
stable under rename, and gives the designer nothing to bind a schema to.

**Severity** Blocking (against the estate standard). **Fix** GUIDs, recorded in a bindings file —
see §6.

### B3 · Every connector binding is internally inconsistent

Each of the thirteen connector actions declares:

```json
"host": { "apiId": "/providers/…/apis/shared_sharepointonline", "connection": "shared_sharepointonline-1" }
```

and each `allConnectionData` entry answers with

```json
"api":        { "id": "/providers/…/apis/shared_sharepointonline" },
"connection": { "id": "/providers/…/apis/shared_sharepointonline/connections/3f1943c5…" },
"referenceKey": "shared_sharepointonline-1"
```

`referenceKey` matches the action, so half the binding looks right. The api id and the connection
id are built from `shared_sharepointonline` while the action binds to `shared_sharepointonline-1`,
so the other half does not — 26 failures, two per action. The thirty-four committed packages all
use the bare `shared_sharepointonline`, which is what the tenant's own `flow_run_record` files
record.

An action that pastes in unbound shows a broken-connection badge and the flow cannot be saved
until someone notices — loud in the designer, silent in the JSON, which is the wrong place to
find it.

**Severity** Blocking. **Fix** one api name everywhere.

### B4 · The file is a designer copy, not a package

```json
"serializedValue": { "runAfter": { "Scope_Global_System_Endpoints": ["Succeeded","Failed","TimedOut","Skipped"] } }
```

A clipboard package is a root — it is dropped into a flow and has nothing to wait for, so every
package in this repository ships `runAfter: {}`. A filled-in anchor means the scope was pasted
into a flow and then copied back out, and the anchor is whatever it happened to land under. The
repository has met this before: a definition came back for review carrying
`"runAfter":{"Initialize_variable_varBulkResults":…}` because a scope had been round-tripped
through the designer, and the round trip rewrites more than the anchor.

**Severity** Blocking for reuse; a strong signal the file is not the source of truth for itself.

### B5 · Six variables that no flow in this estate declares

`EnvironmentName`, `NotificationCorrelationId`, `FlowsFoundDetails`, `FlowsNotFoundDetails`,
`RetrievalErrors`, `FlowsNotFoundCount`. None appears in this repository, in any of the fourteen
variables companions, or in the 504 `InitializeVariable` actions across the 58 tenant exports. The
estate's convention is `var<Name>` and its standard block is `varStatusCode`, `varData`,
`varErrors`, `varRequestId`, `varStartTicks`, `varReceivedAtUtc`, `varCompletedAtUtc`,
`varDurationMs`.

Worse than the naming: **`coalesce()` does not short-circuit.** Every argument is evaluated, so

```
@coalesce(variables('EnvironmentName'), workflow()?['tags']?['environmentName'], 'UnknownEnvironment')
```

does not degrade gracefully when the variable is absent — it throws. The fallback chain reads as
defensive and is not. The same expression appears three times in `Compose_Persistence_Identity`
alone.

**Severity** Blocking. **Fix** `workflow()?['tags']?['environmentName']` needs no variable at all;
Power Automate populates it on every run.

### B6 · `CreateFile` never names the library

```json
"folderPath": "@concat('/history/', …environmentId…, '/', …flowId…, '/', …runId…)"
```

All twelve `CreateFile` actions in the deployed corpus begin their `folderPath` with the library:
`/NITDA_Central_Registry`, `/Portal Attachments`, `/DocTrak_Documents`. This one begins with
`/history/`, which names no library on any site in the tenant. The `artefactLibrary` field is
composed in `Compose_Persistence_Identity` and then **never used by any action**.

**Severity** Blocking at run time. **Fix** put the library segment in the path.

### B7 · The folders created and the files written are two different paths

The three folder actions use `history/…` (no leading slash); the five file actions use
`/history/…` (leading slash). Even if the library were named, the folders prepared and the
folders written into would not be the same folders.

**Severity** Blocking at run time.

## 3. Security and governance findings

### S1 · The record carries the flow's own trigger URL and signature token

`Compose_Complete_Lossless_Record` composes:

```json
"trigger": {
  "headers": "@outputs('Compose_Redacted_Headers')",
  "queries": "@outputs('Compose_Redacted_Queries')",
  "body":    "@triggerBody()",
  "outputs": "@triggerOutputs()"
}
```

The first two are redacted. The fourth is the **whole trigger output object, headers included and
unredacted** — which is where `x-ms-igw-external-uri` and `x-ms-igw-raw-target` live. Those two
gateway headers carry the inbound request URL exactly as received, which for an HTTP-triggered
flow is the trigger URL and its `sig=` token.

That object is then:

1. stringified into `Compose_Complete_Record_String`,
2. written to SharePoint as `complete-run-record.json`,
3. described, in the same record, as

```json
"credentialContainment": { "credentialsExcluded": true, "signedUrlsExcluded": true }
```

Composing a redacted copy of the headers and then writing the unredacted original beside it is
worse than not redacting at all, because the redacted copy is what a reviewer will read. This is
the exact defect check 9b of `verify-designer-paste.mjs` exists to prevent, described there as:
"a flow that captures them mails out a live credential each time it is called."

**Severity** High. **Fix** do not read `triggerOutputs()`. The host's redaction actions already
produce what the record needs.

### S2 · It reverses a ratified governance position, silently

`docs/reference/http-flow-registry-spec.json` ships two configuration seeds:

| Seed | Value | Description in the workbook |
|---|---|---|
| `CaptureRequestBody` | `false` | "Raw HTTP request-body capture is disabled." |
| `CaptureHeaders` | `false` | "Raw HTTP header capture is disabled." |

and `tests/http-flow-registry.test.mjs` holds them there deliberately:

> The workbook disables raw request-body and header capture on purpose — 12_Risks_Controls calls
> endpoint and execution metadata the privacy exposure of this design. A seed flipped to true is
> a governance change, not a configuration tweak, and it should not pass silently.

This package captures both. Not by flipping the seed, where the test would have caught it, but
inside a `Compose` action in a different tree.

**Severity** High. **Fix** capture what the seeds allow, and name the withheld fields in the
record so the omission is visible rather than silent.

### S3 · Two unbounded `result()` expansions are persisted

```json
"scopeResults": { "registryProcessing": "@result('Scope_Flow_Registry_Processing')", "reporting": "@result('Scope_Reporting')" }
```

`result()` returns every contained action's **inputs and outputs**, unredacted and with no size
bound, for every action in that scope. Whatever those two scopes touched — request bodies, list
rows, connector responses — is copied into the record and written to SharePoint. It is also the
single largest contributor to the size problem in C13.

**Severity** High. **Fix** the record needs the scope's *status*; `actions('X')?['status']` is one
short string. Keep `result()` for the catch scope, whose output stays in the run history.

### S4 · `IntegrityVerified: true`, beside a manifest that verifies nothing

```json
"integrityMethod": "SharePoint versioning and immutable HistoryKey",
"item/IntegrityVerified": true
```

No digest is computed anywhere in the package — the workflow definition language has no hashing
function, so none can be. "Immutable HistoryKey" describes an intention; nothing enforces
immutability, and the list that would carry the key does not exist. A reviewer who reads
`IntegrityVerified: true` stops asking how integrity is established.

**Severity** Medium-High — it is the class of claim `tests/standing-claims.test.mjs` was written
to stop this estate making. **Fix** record what SharePoint actually returns at write time (`ETag`,
`Size`) and say plainly that no digest is computed.

## 4. Correctness defects

### C1 · The idempotency guard does not guard anything

This is the most consequential behavioural defect in the package.

```
Condition_History_Record_Already_Exists      ← true branch composes a replay result
  actions: { Compose_Idempotent_Replay_Result }
  else:    { }                               ← empty

Scope_Persist_New_History_Record
  runAfter: { Condition_History_Record_Already_Exists: ["Succeeded"] }
```

A condition **succeeds on both branches**. `Scope_Persist_New_History_Record` therefore runs
whether or not the record already exists. On a replay the flow will:

- create the run folder again,
- write all five artefact files again,
- create a **second history item** with the same `HistoryKey`,
- patch the registry again,

and then `Compose_Final_Persistence_Result`, which tests the same `Get_Existing_History_Record`
result, will report:

```json
{ "status": "AlreadyPersisted", "succeeded": true, "idempotentReplay": true }
```

The receipt says nothing was written, at the end of a run that wrote everything twice. In a
system of record, a duplicate that reports itself as a no-op is worse than a visible duplicate.

The empty `else` branch is the author's own evidence of intent: the persist scope was meant to be
in it.

**Severity** Blocking (behavioural). **Fix** move the persist scope into the `else`, and put the
real guard where it cannot be raced — see C6.

### C2 · `RunStatus` is the literal `"Succeeded"`

In all three item writes. The scope's own `runAfter` is:

```json
"runAfter": { "Scope_Global_System_Endpoints": ["Succeeded","Failed","TimedOut","Skipped"] }
```

so it runs precisely when the work it reports on failed, timed out or never ran — and records it
as a success every time. For a database whose stated purpose is to be accurate and reliable, this
one field makes every row unusable: a query for failures returns nothing, always.

**Severity** Blocking (behavioural). **Fix** derive it. `varStatusCode` is the estate's standard
outcome variable.

### C3 · `DurationMilliseconds` is the literal `0`

Every row records a zero-millisecond run. `varStartTicks` is initialised to `ticks(utcNow())` in
every conforming flow in this estate precisely so duration can be computed.

### C4 · Three more values are guesses recorded as facts

`Criticality: "Medium"`, `DataClassification: "Restricted"`, `ContainsSensitiveData: true` — all
literals, on every row, for every flow. `Criticality` in particular is the field an alerting rule
would key on.

### C5 · The registry patch discards the registry's history

`Update_Current_Registry_Item` writes all 28 columns from the current run. On the estate's
designed registry — which carries `TotalExecutions`, `SuccessfulExecutions`, `FailedExecutions`,
`ConsecutiveFailures`, `AverageDurationMs` and `RecordVersion` — a blind patch resets the estate's
entire execution history on every single run. The one field a "consecutive failures" alert
depends on can never exceed the value this run wrote.

**Fix** read the row back and increment. The rebuild does this in `Compose_Registry_Rollup`.

### C6 · Two concurrent runs create two registry rows

`Get_Current_Registry_Item` → condition → create-or-update is a read-modify-write with no lock and
no unique constraint. Two runs of the same flow that overlap both see "not found" and both create.
The history list is safe only by accident — its key contains the run id.

**Fix** the estate's design already solves this: `RegistryKey` is declared **indexed and unique**
on `DGO_HTTPFlowRegistry`, `ExecutionKey` likewise on `DGO_HTTPFlowExecutionLedger`. With those in
place SharePoint refuses the loser of the race, and the read-before-write becomes an optimisation
rather than the guard.

### C7 · Three unguarded `length()` calls

```
@length(body('Get_Existing_History_Record')?['value'])
@length(body('Get_Current_Registry_Item')?['value'])
@if(greater(length(body('Get_Existing_History_Record')?['value']),0), …)
```

`length(null)` throws. A GetItems that returns a body without `value` — a throttled response, a
partial failure — faults the condition rather than taking the false branch. The estate's idiom is
`coalesce(outputs('X')?['body/value'], json('[]'))`, used throughout `DGO_SCHEDULED_SWEEP`.

### C8 · `greater(variables('FlowsNotFoundCount'), 0)` on an undeclared variable

Both item writes carry it. See B5.

### C9 · Every stored URL is broken by the first space

```
@concat('https://nitdanigeria.sharepoint.com', outputs('…')?['body/Path'])
```

`Path` is a server-relative path containing the library title. The libraries in this tenant have
spaces in their names (`Portal Attachments`, and the proposed `NITDA Flow Truth Artefacts` has
three). An unencoded space produces a URL that resolves for nobody — and these URLs are the only
pointer from the database row to the artefact it describes.

### C10 · `ComplianceIssuesJson` stores notification delivery

```json
"item/ComplianceIssuesJson": "@string(outputs('Compose_Governance_Record')?['notification_delivery'])"
```

A column named for compliance issues, populated with a delivery record. Anyone querying for
compliance issues gets the wrong data and no error.

### C11–C12 · Three columns carry the wrong identity

`item/EnvironmentName` is set to `environmentId` — the same value, in two columns, so the display
name is unavailable. `item/FlowName` is set to `workflow()?['name']`, which is the flow's **GUID**,
not its name; `workflow()?['tags']?['flowDisplayName']` is the name and is already available.

### C13 · `lossless: true`, `truncated: false`, `captureMode: "Complete"` — all unconditional

Nothing measures the record. It embeds the full flow resource, the full `workflow()` object, the
full trigger outputs, the inventory, the governance record and two `result()` expansions. On a
flow of any size that is megabytes, and the only thing that happens when it exceeds what an action
or a list column will hold is that something fails at run time — after the file writes have
already partly succeeded, since the string is composed first and the guard does not exist.

### C14 · `contentSizeBytes` is a character count

`length()` over a string counts characters. The stored file is UTF-8. The field is off by however
many multi-byte characters the record contains, under a name that says bytes.

### C15 · An append-only list with no index strategy

`Get_Existing_History_Record` filters the history list with `$top: 1` and no `$orderby`. The
history list gains one item per run and is unbounded. SharePoint refuses any query it cannot
resolve through an index once a list passes 5,000 items — this estate has already met that failure
in production:

> `{"status":400,"message":"The attempted operation is prohibited because it exceeds the list view threshold."}`

on a list of 15,804 items, twice, and the fix documented in `scripts/build-scheduled-sweep.mjs`
required both an index and a bounded window. A `HistoryKey eq` filter on an **indexed** column is
fine; on an unindexed one it fails, permanently, on a date nobody can predict.

### C16 · A null HTML report aborts the chain after two files are written

`Create_Complete_HTML_Report_File` writes `@outputs('Compose_Enterprise_Branded_HTML_Report')`
with no fallback. If the reporting scope was skipped or failed, that is null; `CreateFile` fails;
the strict `["Succeeded"]` chain stops — after the run record and the flow resource have already
been written, and before the history item exists. The run leaves two orphan files and no row.

### C17 · Four timestamps from four separate `utcNow()` calls

`capturedUtc` in the identity, `capturedUtc` in the record, `CompletedUtc` and `PersistedUtc` in
each item write. They will differ, and the record contains no single instant to reconcile them
against.

### C18 · `Scope_Persistence_Failure` does not cover `Skipped`

`Compose_Final_Persistence_Result` requires the persist scope in `[Succeeded, Failed, TimedOut]`.
Once C1 is fixed and the persist scope moves under a condition, `Skipped` becomes reachable and
the final Compose would itself be skipped. The status sets have to be re-derived together with the
structural fix, not after it.

## 5. Alignment — the estate already designs this database

This is the finding that reframes the rest.

`docs/reference/http-flow-registry-spec.json` is the extraction of
`docs/reference/http-flow-registry-workbook.xlsx`, the design of
`Scope_01_GOV_Provision_HTTP_Flow_Registry_COMPLETE_UPDATED`. It specifies, on
`/sites/DGO_ECM_GOVERNANCE`:

| List | Fields | Unique key | Purpose |
|---|---|---|---|
| `DGO_HTTPFlowRegistry` | 35 | `RegistryKey` | Current authoritative HTTP flow truth |
| `DGO_HTTPFlowExecutionLedger` | 15 | `ExecutionKey` | Execution ledger |
| `DGO_HTTPFlowContractVersions` | 13 | `ContractKey` | Contract versions |
| `DGO_HTTPFlowDependencies` | 9 | `DependencyKey` | Dependencies |
| `DGO_HTTPFlowRegistryExceptions` | 12 | `ExceptionKey` | Exceptions |
| `DGO_HTTPFlowRegistryConfiguration` | 6 | `ConfigKey` | Configuration |
| `DGO_HTTPFlowConsumerRegistry` | 11 | `ConsumerKey` | Consumers |

101 fields, seven unique keys, twelve configuration seeds, seven views with their CAML, versioning
on every list. The submitted package invents a parallel three-list store on the **activity-tracking
site** — and keys it on `RegistryKey`, the same name.

Two registries of one estate is how a fact gets recorded twice and reconciled never. And the
designed one is not merely an alternative; it is strictly better for every defect above:

| Defect | What the designed schema already provides |
|---|---|
| C1, C6 duplicate rows | `RegistryKey` and `ExecutionKey` indexed **and unique** — the database is the guard |
| C2 hardcoded status | `Outcome`, a field, not a literal |
| C3 zero duration | `DurationMs` |
| C5 discarded counters | `TotalExecutions`, `SuccessfulExecutions`, `FailedExecutions`, `ConsecutiveFailures`, `AverageDurationMs` |
| C15 threshold failure | `ExecutionKey`, `RegistryKey`, `RunId`, `StartedUtc`, `Outcome` all declared indexed |
| — | `RecordVersion` for optimistic concurrency; `IsCompliant` / `ComplianceIssues` as separate fields |
| S2 capture policy | `CaptureRequestBody=false`, `CaptureHeaders=false`, already ratified and gated |

**Neither database exists.** `tests/http-flow-registry.test.mjs` asserts that none of the seven
lists appears in the 2026-08-18 capture of the target site, and will go red the day one does. So
the choice is not between a built store and an unbuilt one — it is between provisioning a design
that has been through review, and provisioning a second one that has not.

The rebuild targets the designed schema. If the agency rules otherwise, the site, the list titles
and their GUIDs are all in one file — `docs/deployment/governance/list-bindings.json` — and
nothing else changes.

## 6. Efficiency and effectiveness

| # | Finding | Cost | Fix |
|---|---|---|---|
| E1 | Three `CreateNewFolder` calls build a three-level path one level at a time, each tolerating the last one's failure — and write to a path the file actions do not use | 3 connector calls per run, all wasted | One tolerant call for the whole path (`CreateNewFolder` takes a relative path) |
| E2 | Five `CreateFile` actions chained on `["Succeeded"]` | 5 round trips serialised, ~2s of avoidable latency, and a failure at file 3 leaves 2 orphans | Four content files as parallel branches; the manifest waits on all four |
| E3 | The complete record is composed **and stringified** before the idempotency probe runs | On a replay, megabytes of `string()` for nothing | Probe first. One `GetItems` is cheaper than the capture |
| E4 | Two `result()` expansions, the full `workflow()` object and the full `triggerOutputs()` inside the persisted record | The dominant size contributor; also S1 and S3 | Named fields and scope statuses |
| E5 | The 28-column registry field block is written twice, differing only by `id` | Two blocks kept in step by hand; a column added to one is a silent divergence between the row created and the row updated | Compose the block once, spread it into both writes |
| E6 | Neither `GetItems` uses `$select` | Whole rows fetched to read one `ID` | `$select` — or, for the rollup, fetch exactly the counter columns |

## 7. The rebuild

`scripts/build-flow-truth-persistence.mjs` → `docs/deployment/governance/flows/`.
30 actions, 11 connector actions, 0 findings from `tests/designer-paste-schema.test.mjs`.

**Structure**

```
Compose_Host_Inputs              one funnel for all eight host actions and four variables
Compose_Persistence_Identity     keys, folder path, display name
Compose_Run_Timing               the only place a date is guarded
Compose_Run_Outcome              outcome, duration, error count — all derived
Compose_Capture_Policy           what is captured and what is withheld, by name
Get_Existing_Ledger_Record       the probe, before anything expensive
Condition_Ledger_Record_Already_Exists
  ├── true   Compose_Idempotent_Replay_Result
  └── else   Scope_Persist_New_Ledger_Record
               record → string → budget → clamp
               one tolerant folder create
               four files in parallel
               Compose_Integrity_Manifest      (ETag + Size, no digest claimed)
               Create_Integrity_Manifest_File
               Create_Ledger_Item
               Get_Current_Registry_Item → Compose_Registry_Rollup
               Condition_Registry_Item_Exists → Update | Create
               Compose_Persistence_Receipt
Scope_Persistence_Failure        catch, runAfter Failed/TimedOut — the only result()
Compose_Final_Persistence_Result
```

**Every finding, and where it went**

| Finding | Disposition |
|---|---|
| B1 lists do not exist | Targets the designed governance lists; blocked state recorded in `list-bindings.json` and asserted by the test |
| B2 title targeting | GUIDs the moment the bindings file carries them; the title fallback **is** the visible marker of the blocked state |
| B3 connector bindings | One api name; the generator emits `allConnectionData` from the actions, so they cannot disagree |
| B4 anchored scope | `runAfter: {}`, asserted |
| B5 undeclared variables | Four estate-standard variables, read in one action, with a companion that declares exactly those |
| B6/B7 folder paths | One `artefactFolderPath` field, library segment included, used by every file and folder action |
| S1 trigger URL | `triggerOutputs()` and `triggerBody()` are never read; asserted as a negative control |
| S2 capture policy | `Compose_Capture_Policy` states both seeds and names the withheld fields |

**One idiom worth stating on its own.** The workflow definition language evaluates **both arms of
`if()`**. A guard written as `if(greater(length(s),n), substring(s,0,n), s)` computes the substring
on the short string too, and throws there. Every clamp in the rebuild is written
`substring(s,0,min(length(s),n))`, which is valid at every input length, and the test asserts that
no other form appears.

**What the rebuild does not do.** It computes no content digest, because the language has no
hashing function; the manifest says so. It cannot be pasted until the two lists and the library
are provisioned. And it remains a fragment of a larger flow — eight host actions are save-time
dependencies. What changed is that they are declared, in
`DGO_FLOW_TRUTH_PERSISTENCE.host-contract.json`, read in one place, and each read is null-safe.
