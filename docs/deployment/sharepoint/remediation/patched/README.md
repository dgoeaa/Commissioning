## How to apply one

From `C:\Commissioning`, in the same Windows PowerShell window that holds your
`Add-PowerAppsAccount` sign-in.

**Dry run first — this sends nothing:**

```powershell
.\scripts\update-flow-definition.ps1 -EnvironmentName Default-ca6a4b3f-9123-49bc-bcb9-27085ebbf1a1 -FlowId 3b69aa71-ffed-4956-9d20-2aa3021a8da0 -DefinitionPath .\docs\deployment\sharepoint\remediation\patched\Portal_Verify_Confirm.definition.json
```

It prints the flow's name and current action count, writes the **current** definition beside the
patch as `Portal_Verify_Confirm.definition.before.json`, and stops. Read that output before
going further.

**Then apply**, by adding `-Apply` to the same command.

**Then confirm:**

```powershell
.\scripts\export-power-automate-flows.ps1 -EnvironmentName Default-ca6a4b3f-9123-49bc-bcb9-27085ebbf1a1 -OutDir .\docs\reference\flow-contracts\deployed -WorkflowId 3b69aa71-ffed-4956-9d20-2aa3021a8da0
.\scripts\redact-signed-urls.ps1 -Path .\docs\reference\flow-contracts\deployed
node scripts/flow-list-sweep.mjs --write ; node scripts/verify-portal-wiring.mjs
```

Target after this one flow: **15/59 operations, 2/7 endpoints, 12 boundary crossings.**

The denominator is 59 across seven endpoints since [D11](../../DECISIONS.md) put WRITEBACK in
scope. These five visits close 49 of the 59.

## To put it back

The `.before.json` the dry run wrote is the flow exactly as it was. Feed it to the same script
with `-Apply` and the flow returns to that state.

## Why not the package route

Legacy package import refuses to **update** these flows and offers only "save as a new flow".
A new flow is a new trigger URL, and the portal's `config.local.js` holds the old one. Package
export stays useful as a way to *read* a definition; it is not a way to write one.
