Common mechanics

Every request below is a flat JSON object — no portal request is ever wrapped in an action/operation field, a requestId, or a timestamp, unlike the internal operations platform's convention. Every response is parsed by the same permissive helper, and every endpoint degrades the same two ways when unconfigured or offline.

Response parsing

function readJson(r) {
  return r.text().then(function (t) {
    var data = {};
    try { data = t ? JSON.parse(t) : {}; } catch (e) {}
    return data;
  });
}

A non-JSON or empty body resolves to {} silently — never throws. Every field this document lists as “read” is read with optional-chaining-style access; an absent field is simply undefined.

KeyQueued for retryResult
SUBMISSIONYES{delivered:false, reason:'offline'}

PF.outbox queues only submission/support entries, capped at the 50 most recent, retried up to 5 times whenever PF.outbox.flush() runs with connectivity restored.

Findings

  • verification-required is classified identically to every other queued failure — submit.js has no branch that re-runs VERIFY/VERIFY_CONFIRM the way track.js does for STATUS.
  • uploadAll() runs zero iterations when res.uploads is empty (the live-observed case) — attachments are silently never transmitted while the submission still reports delivered.
02

UPLOAD

PUT · PF.intake.upload(ticket, file) · core.js:370

Request — as sent by the client

Called once per declared attachment, sequentially, from submit.js's uploadAll (line 426).

PUT <UPLOAD endpoint URL>
Content-Type: application/octet-stream
X-Upload-Ticket: <ticket, exactly as returned in SUBMISSION's uploads[].ticket>

Body: <raw bytes of the file, unencoded>

Trigger and actions — real, as provided

Not harvested and not from the live probe — this is the flow's actual definition, supplied directly. It supersedes every earlier statement that this flow was unbuilt; it exists. Trigger: Request, kind Http, method PUT, no body schema declared.

1. Compose_Upload_Ticket
   @trim(string(coalesce(
     triggerOutputs()?['headers']?['x-upload-ticket'],
     triggerOutputs()?['headers']?['X-Upload-Ticket'], '')))

2. Condition_Upload_Ticket_Missing — If empty(ticket) == true

   TICKET ABSENT/EMPTY →
   Response_Upload_Ticket_Missing
     HTTP 403
     { "stored": false, "reason": "missing-upload-ticket" }

   TICKET PRESENT (the only condition checked) →
   3. Compose_Upload_FileName
      @concat(formatDateTime(utcNow(), 'yyyyMMdd-HHmmss-'),
        replace(replace(outputs('Compose_Upload_Ticket'),
        '/', '-'), ':', '-'), '.bin')
      → extension is ALWAYS .bin; no original filename
        is read from the request anywhere in this flow

   4. Create_file_Upload  (SharePoint CreateFile, chunked)
      site:   https://nitdanigeria.sharepoint.com/sites/NEDMS
      folder: /NITDA_Central_Registry
      name:   the composed .bin filename
      body:   @triggerBody()  — raw bytes, unexamined

   5. Compose_Upload_Response_Body
      {
        "stored": true,
        "attachmentLink": coalesce(body/Path, body/Id, body/Name),
        "ticket": "<the ticket>",
        "fileName": "<the composed .bin filename>"
      }

   6. Response_Upload_Success  →  HTTP 200

FAILURE PATH (Create_file_Upload fails: throttling,
permission, invalid name) →
   Response_Upload_Failed
     HTTP 500
     { "stored": false, "reason": "upload-processing-failed",
       "details": "<failed action's result object>" }

Every branch sends Access-Control-Allow-Methods: PUT, OPTIONS and Access-Control-Allow-Headers: Content-Type, X-Upload-Ticket, X-Correlation-ID. No Access-Control-Allow-Origin header is set anywhere in this definition — whether a cross-origin browser fetch() can still read the response depends on platform-level CORS handling this definition does not settle, and is worth confirming against a real browser call.

CRITICAL
The ticket is never validated against anything SUBMISSION issued. Condition_Upload_Ticket_Missing checks only that the header is present and non-empty — no lookup, no expiry check, no single-use enforcement. Any non-empty string in X-Upload-Ticket satisfies the only gate this flow has. Combined with the endpoint URL being delivered to every visitor's browser, this is an unauthenticated write path into the agency's SharePoint registry.

Further gaps against the documented obligation

  • No file size limit is enforced.
  • No integrity check (SHA-256 or otherwise) against any declared digest — triggerBody() is written to SharePoint unexamined.
  • No association is recorded between the stored file and the correspondence record it belongs to — the ticket is sanitised into a filename fragment, never decoded or looked up. Combined with the forced .bin extension and the absent original filename, a stored file has no machine- or human-readable link back to its submission, name, or real content type.

Handling branches

2xx, data.stored === true{ok:true, stored:true}
Non-2xx{ok:false, stored:false, reason}

There is no stored:false branch on a 200 in the real flow — every path reaching Create_file_Upload returns stored:true. The outcomes are exactly two: a clean 200, or a 500 from the underlying SharePoint call failing outright.

DEAD CODE
support.js's send() calls PF.intake.support({...}) with no .then(), no assignment. VERIFY

POST · PF.intake.verifyRequest(email) · core.js:417 · shares the platform's OTP_GENERATE flow

Request — as sent by the client

Called from track.js's requireVerification (line 174), only after STATUS answers verification-required.

{ "email": "<the address entered in the tracking form>" }

No action, operation, or purpose field — this is the entire body.

Trigger schema — harvested, shared, mismatched

Source: the harvested OTP_GENERATE definition (docs/reference/foundational/flows/definitions/OTP_FLOWS/OTP_GENERATE/). Accepted top-level properties: action, operation, mode, source, userEmail, method, id, device, otp_code (additionalProperties: true).

MISMATCH
email is not a named property of this schema. The flow's routing keys on action === 'generate'|'verify' and an identifier field — this request supplies neither.

Response

Documented target

{
  "sent": true,

confidence and results appear on every OTP-family response in this estate and are not part of any documented contract for either app.

Caller branch

Proof lifecycle

Held in a page-scoped JavaScript variable only (var proof = null;, track.js:143) — never persisted. Consumed by exactly one immediately-following STATUS call, then reset to null. A page reload discards it; there is no path for a stale proof to be replayed.

LIVE EFFECT
On the live-observed response (verification absent), track.js's !v.ok || !v.verification branch takes the failure path — the citizen sees “That code was not accepted,” indistinguishable from a genuinely wrong code.

Cross-cutting behaviour

  • Demo modePF.backendConfigured() reflects whether the SUBMISSION endpoint has a configured URL — that one key alone gates whether the entire portal is considered live, independent of the other five endpoints' configuration.
  • Draft autosaveEntirely client-local (localStorage). No flow is involved. Attachment bytes are explicitly excluded from the saved draft — only {name, size} survives.
  • Reference mintingThe tracking ID shown immediately after submitting is client-generated (PF.uid()), before the registry is contacted, and is overwritten by the registry's referenceId if one arrives. The help-case reference (sref(), NITDA-S-XXXXXX) is likewise client-generated and, per §03, never reconciled with the flow's own reference.
  • Filename policyNo client-side normalisation exists in submit.js or core.js — the Universal Filename Policy is applied by the SUBMISSION flow itself.
